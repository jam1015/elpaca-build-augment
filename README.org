An extension for [[https://github.com/progfolio/elpaca][Elpaca]] that runs the
per-package build steps GNU/NonGNU ELPA and MELPA run on their build
servers. Without it, packages that rely on those steps install from source
in an incomplete state.

* The problem

Elpaca installs a package by cloning the source, byte-compiling the elisp,
and generating autoloads. For most packages that is enough. For about 16% of
GNU/NonGNU ELPA packages and a smaller slice of MELPA, upstream also runs
extra build steps that Elpaca skips.

Some examples of what goes missing:

- AUCTeX ships =latex/preview.sty= only after =make elpa= runs. Without
  that, =preview-latex= fails at LaTeX time with =File 'preview.sty' not
  found.=
- ESS, Eat, Evil, Bongo and many others ship Info manuals that only exist
  after =makeinfo= runs. Some need a =cd= into =doc/= so =@include= paths
  resolve; some need a preceding =make= target to generate =version.texi=.
- Hyperbole, Tramp, flymake-collection and a few others need a =make=
  target that writes a =.el= file.

=package.el= sidesteps all of this by downloading pre-built tarballs.
Elpaca installs from source, which lets you pin commits, follow branches,
and patch locally, but every upstream build step has to run on your
machine. This package runs them.

* How it works

The package adds one hook to =elpaca-recipe-functions=. For each package
Elpaca resolves, the hook picks one of three paths.

** ELPA path, with build commands

If the package has a =:make=, =:doc=, or =:shell-command= entry in
GNU/NonGNU ELPA's =elpa-packages= file, the hook synthesizes those
commands:

#+begin_example
:shell-command CMD   ->  sh -c CMD        in source dir
:make TGT            ->  make TGT         in source dir
:doc "D/F.texi"      ->  cd D && makeinfo F.texi -o F.info
:doc "D/F.org"       ->  cd D, export F.org to .texi via ox-texinfo,
                         then makeinfo on the result. Covers packages
                         whose :doc source is a README.org (corfu,
                         consult, vertico, etc.).
#+end_example

The =elpa-packages= file is fetched on first use and cached.

The hook then mirrors ELPA's packaging rule (ship everything in source
minus a known-junk list), honoring =:lisp-dir=, =:ignored-files=, and
=:excludes= from the same entry.

** ELPA path, no build commands

For ELPA entries that declare nothing beyond a =:url= (geiser-mit,
package-lint, evil-collection, dash, and many others), the hook still
runs the whole-source packaging step. ELPA's =elpa-admin.el= applies
the same "ship everything in source" rule to every entry, regardless
of whether build commands are declared, so non-elisp files like data
tables, snippets directories, Scheme glue, and images get into the
build dir.

** Heuristic path

For packages with no ELPA entry at all (MELPA-only), the hook scans
the source tree for =.texi= files. Files that look like standalone
manuals (contain =@setfilename= or start with =\input texinfo=) are
compiled with =makeinfo --force= from their own directory so
=@include= paths resolve. Fragments like =fdl.texi= and =gpl.texi=
are detected and skipped.

This path has no upstream metadata to lean on and makes no
guarantees. It handles the common case: one =.texi= manual, maybe a
few fragments, no exotic build. For stranger builds (texi generated
by a Makefile target, texi fetched over the network at build time,
nested manuals, custom makeinfo flags), write your own =:build= for
that package.

** Existing =:build= fields are respected

Recipes that already declare =:build= (for example =elpaca-menu-org='s
custom pipeline for Org) are left alone.

** Info integration

Both paths disable Elpaca's default =elpaca-build-docs= step (which has
multi-file =makeinfo= bugs) and queue =elpaca--install-info= so the Info
=dir= entry gets updated.

* Companion: audit against =package.el=

The sibling file [[file:elpaca-build-augment-audit.el][elpaca-build-augment-audit.el]] checks that an Elpaca
install has every file a =package.el= install would have. It downloads
the latest tarball from GNU ELPA, NonGNU ELPA, or MELPA for a package you
have installed and diffs the two trees.

The question it answers: for this package, am I missing anything that
=package.el= users would have gotten?

Even with =elpaca-build-augment= replaying the upstream build steps
locally, an independent check is useful. Run the audit when you first
install a new package, or when a feature that should work does not.

** What gets compared

File basenames only, not full paths. =package.el= flattens the layout
and Elpaca preserves the repo tree, so path-level diffs are noise.

Elisp output and metadata are filtered out by default (customizable via
=elpaca-build-augment-audit-ignore-regexps=):

- =*.el=, =*.elc=
- =*-autoloads.el=, =*-pkg.el=
- =dir=, =.dir-locals.el=
- =LICENSE=, =COPYING=, =COPYRIGHT=
- =README*=, =NEWS=, =AUTHORS=, =ChangeLog*=, =TODO=
- =*.md=, =*.rst=, =*.org=, =*.txt=
- VCS droppings

What is left is what you care about: =.info= manuals, =.sty= and =.cls=
style files, images, data files, templates.

** Entry points

- *=M-x elpaca-build-augment-audit=.* Prompts for one package out of
  everything Elpaca currently has queued. Extracts the tarball under
  =elpaca-build-augment-audit-cache-dir= (default
  =<user-emacs-directory>/elpaca-build-augment-audit-cache/<pkg>-<version>/=)
  and shows a one-row tabulated-list buffer with the diff. Refetches
  =archive-contents= every call; the tarball itself is cached on disk
  across runs (see "Audit cache behavior" below).

- *=M-x elpaca-build-augment-audit-all=.* Iterates over every queued
  package. The tabulated-list buffer is sortable; sort by =Status= to
  pull =GAP= rows to the top. First run is slow (one tar fetch per
  package); later runs hit the on-disk tarball cache at
  =elpaca-build-augment-audit-cache-dir=. =archive-contents= is
  refetched once per run and reused across all packages.

- *=elpaca-build-augment-audit-watch=.* A defcustom list of packages
  audited automatically after Elpaca finishes init. Each result is
  written as one line to =*Messages*=, so if a future upgrade silently
  drops =auctex.info= you see it the next time Emacs starts. Opt-in by
  design: the network fetch and tar extraction do not belong on every
  normal startup. The watch list is for packages you have been bitten
  by before. Same caching behavior as the other entry points.

  #+begin_src elisp
  (setopt elpaca-build-augment-audit-watch '(auctex ess eat bongo))
  (elpaca-build-augment-audit-enable)
  #+end_src

** Report columns

| Column  | Meaning                                                              |
|---------+----------------------------------------------------------------------|
| Package | Symbol you asked about                                               |
| Archive | =gnu=, =nongnu=, or =melpa=, whichever carries it                    |
| Version | Latest tarball version at audit time                                 |
| Status  | =ok=, =GAP=, =not-built=, =no-tarball=, or =error:MSG=               |
| Pinned  | =ref:...=, =tag:...=, =tar:...=, =branch:...=, =version:...=, or empty |
| Missing | First few basenames present in tarball but not in the build         |

=no-tarball= means =package.el= cannot install the package at all:
github-only recipes, local recipes, or GNU ELPA =:core= packages. Not a
problem, just nothing to compare against.

** Pinned recipes

If your Elpaca recipe sets =:ref=, =:tag=, =:tar=, =:branch=, =:version=,
or =:pin=, the installed source is held at a specific point in history.
(=:tar= is set by every GNU ELPA menu entry to track the archive's
released version; when it matches the archive's latest version exactly,
no skew is possible and the =Pinned= column stays empty.) The archive
only serves the latest tarball, and MELPA will not serve old ones at
all, so a =GAP= on a pinned package may be a real missing build
artifact or may just reflect that upstream has moved on and the newer
tarball ships a file your pinned revision never had.

The =Pinned= column surfaces the ref so you can tell the difference.
Investigate the =GAP= rows; ignore the ones that line up with the pin.

** Version mismatch is expected

Elpaca tracks a git commit; =package.el= ships a dated snapshot of the
same upstream. The audit compares the latest tarball against your
current build, not matching versions. Filename-level parity is
version-insensitive for the things that matter (did the =.info= manual
get built, did the =.sty= files land), so this is fine, but worth
knowing.

** Audit cache behavior

Every audit refetches each archive's =archive-contents= (a few hundred
KB) so the latest upstream version is always seen. The tarball itself
is only downloaded when the cached =<pkg>-<version>/= directory is not
present on disk, which happens in two cases:

- First audit of a package.
- Upstream published a new version since the last audit. The old
  =<pkg>-<oldversion>/= dir is deleted before the new one is fetched,
  so the cache does not grow unbounded.

There is no =refresh= command; refresh is implicit.

** Audit system requirements

=tar= on =PATH=. The URL fetches use Emacs's built-in =url.el=; no
=curl= needed.

* Installing

Requirements on =PATH=: =makeinfo= (from texinfo), =make=, =sh=. On
Windows, MSYS2 or Git for Windows provides all three.

The block below goes after Elpaca's own installer boilerplate. See
[[https://github.com/progfolio/elpaca/blob/master/doc/manual.md#installer]]
for the boilerplate.

#+begin_src elisp
;; :wait t tells Elpaca to install this package and run the body
;; before continuing. The hook has to be registered before any later
;; (elpaca ...) or (use-package :ensure t) form is evaluated.
(elpaca (elpaca-build-augment
         :host github
         :repo "jam1015/elpaca-build-augment"
         :wait t)
  ;; Optional configuration. All options have defaults; uncomment to change.
  ;; (setopt elpaca-build-augment-sources
  ;;         elpaca-build-augment--sources-savannah)  ; default: emacsmirror
  ;; (setopt elpaca-build-augment-cache-metadata nil) ; default: t
  (elpaca-build-augment-enable)
  ;; Optional: audit builds against package.el tarballs.
  (require 'elpaca-build-augment-audit)
  (setopt elpaca-build-augment-audit-watch '(auctex ess eat))
  (elpaca-build-augment-audit-enable))

;; Elpaca's built-in menu injects :wait t for elpaca-use-package.
(elpaca elpaca-use-package (elpaca-use-package-mode))

(use-package auctex :ensure t :demand t) ; make elpa + makeinfo
(use-package ess    :ensure t)           ; cd doc && makeinfo ess.texi
(use-package eat    :ensure t)           ; makeinfo eat.texi
(use-package bongo  :ensure t)           ; MELPA-only, heuristic path

(elpaca evil)                            ; NonGNU ELPA :doc + :ignored-files
(elpaca sicp)                            ; MELPA-only
#+end_src

On first use the library fetches the =elpa-packages= files from the
emacsmirror GitHub mirrors (by default) into
=<user-emacs-directory>/elpaca-build-augment-cache/=. No metadata ships
with the package.

* Configuration

All options are plain =defcustom=s. Set them with =setopt=, or via =M-x
customize-group RET elpaca-build-augment=.

** =elpaca-build-augment-sources=

Where the =elpa-packages= files come from. Two presets ship with the
package:

- =elpaca-build-augment--sources-emacsmirror= (default). The =emacsmirror=
  GitHub mirrors of =elpa.git= and =nongnu-elpa.git=, served by GitHub's
  CDN.
- =elpaca-build-augment--sources-savannah=. The Savannah cgit endpoints.
  Authoritative, but cgit often returns 502 error pages under load.

You can also set the variable to any alist to point at another host (a
local mirror, a corporate proxy, etc.). See the =defcustom= docstring for
the plist shape.

#+begin_src elisp
(setopt elpaca-build-augment-sources
        elpaca-build-augment--sources-savannah)
#+end_src

** =elpaca-build-augment-cache-metadata=

Boolean. Default =t=.

- =t=. Fetched snapshots persist on disk at
  =<user-emacs-directory>/elpaca-build-augment-cache/= and are reused
  across Emacs sessions. Call =M-x elpaca-build-augment-refresh= to pull
  fresh copies.
- =nil=. No disk cache. Snapshots are fetched once per Emacs session into
  an in-memory index. =M-x elpaca-build-augment-refresh= forces a refetch
  within a session.

Disk caching is the recommended default. The metadata changes slowly, and
a stale copy only costs you a build step or two on recently-added fields.

#+begin_src elisp
(setopt elpaca-build-augment-cache-metadata nil)
#+end_src

** =elpaca-build-augment-audit-watch=

List of package symbols to audit automatically after Elpaca finishes
building them. Only consulted when =(elpaca-build-augment-audit-enable)=
has been called. See the audit chapter above.

#+begin_src elisp
(setopt elpaca-build-augment-audit-watch '(auctex ess eat))
#+end_src

* Introspection

See what the library would do for a specific package:

#+begin_example
M-x elpaca-build-augment-explain RET auctex RET
#+end_example

Prints the ELPA entry (if any) and the exact shell commands that would
run. This reads from the cached ELPA metadata index, loading it on
first call per =elpaca-build-augment-cache-metadata= and
=elpaca-build-augment-sources=. Call =M-x elpaca-build-augment-refresh=
to force a reload from upstream.

* Refreshing the ELPA metadata

Pull fresh snapshots from upstream:

#+begin_example
M-x elpaca-build-augment-refresh
#+end_example

* Overriding on a per-package basis

Nothing library-specific is needed. The hook only sets =:build=, and only
when the user has not. Other recipe fields (=:branch=, =:repo=, =:files=,
=:ignored-files=) can be set inline in =(elpaca ...)= or =(use-package
... :ensure (...))=. Elpaca's recipe merging gives the user's declaration
higher precedence than the menu's. To opt a specific package out of
augmentation, give it an explicit =:build=.

#+begin_src elisp
;; The hook does not touch :branch, so it stays.
(use-package somepkg :ensure (:branch "release"))

;; Opt out of augmentation.
(use-package weirdpkg :ensure (:build nil))
#+end_src

* Limitations

- Packages whose build needs a C compiler plus system libraries
  (pdf-tools' =epdfinfo=, vterm's module, irony-mode's server) install as
  elisp only, same as under vanilla Elpaca and under =package.el=. Run the
  package's own =M-x pdf-tools-install= or equivalent, and install the
  system packages separately.
- GNU ELPA =:core= packages (bind-key, eglot, eldoc, erc, ...) are copies
  of files from Emacs's own source tree, not independent repos. There is
  nothing for Elpaca to clone, so this library cannot install them from
  source. If you want the ELPA-newer version, use =:type tar :inherit
  elpaca-menu-gnu-elpa=.

* Install-time filesystem scan

Both paths walk the package's source tree at install time. The ELPA path
builds a flat =(source-file . build-file)= pair list; the heuristic path
looks for =.texi= manuals. The walk takes about 10 ms per install and only
runs on install or rebuild, not at startup.

The walk is hard to avoid with Elpaca's current internals.
=elpaca-generate-autoloads= and its siblings skip symlinked directories,
so the simpler route of =:files ("*" (:exclude ...))= with a
whole-directory symlink of =lisp/= would hide nested =.el= files from
autoload scanning. Files have to be symlinked one by one.

If Elpaca ever learns to follow directory symlinks, this walk could shrink
or go away.

* Regenerating the manual

=elpaca-build-augment.texi= is generated from =README.org= via
=ox-texinfo=. If you change the README, regenerate and commit it:

#+begin_src sh
make doc        # produces elpaca-build-augment.texi
make info       # optional: locally preview the .info
#+end_src
